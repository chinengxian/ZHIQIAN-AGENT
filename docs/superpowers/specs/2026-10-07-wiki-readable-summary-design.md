# Wiki 可读摘要与可信事实分层设计

## 背景

现有 Wiki 摘要页把用于检索的原子 Claim 逐条渲染为 Markdown 列表，并由前端以纯文本显示。结果既暴露了 `#`、`[^claim]` 等 Markdown 源码，也把文档编号、版本等元数据与正文事实混在一起，无法承担人读摘要的作用。

本设计保留路线 B 的来源驱动混合检索、原子 Claim、主题页和 Agent 可信过滤；新增面向阅读的摘要分段，明确区分人读内容与机器检索内容。

## 目标与范围

### 目标

- 摘要页在首屏展示可在一分钟内读懂的整篇文档概述。
- 每个摘要段落均可追溯到当前有效的原文 Chunk。
- 搜索、主题页和 Agent 继续只消费原子 Claim，不因可读摘要变得冗长或重复。
- 标题优先使用文档内部标题，文档元数据单独展示，不占用摘要正文。
- 已发布旧页面、人工编辑、回滚和来源失效均保持兼容。

### 范围内

- 摘要生成协议、发布模型、页面 API 与前端展示。
- Markdown Front Matter / 文档首个 H1 的 Wiki 标题与元数据提取。
- 长文档的两阶段“原子事实优先、摘要后合成”生成。
- 来源展开、失效提示与 API / Agent 检索隔离。
- 自动化单元、集成、组件及可运行环境下的浏览器验证。

### 范围外

- 独立 Wiki 向量集合、GraphRAG 和路线 C。
- 跨知识库主题归并。
- 把人工编辑的无来源文本自动标为可信。
- 改写既有文档详情页的数据模型；Wiki 来源深链沿用 REQ-007 已有能力。

## 用户体验

摘要页的自动生成版本按以下层级展示：

```text
页面标题
文档信息卡：编号、版本、生效日期、状态、范围、责任部门、替代关系、标签

概述                 [查看 N 个来源]
核心要求             [查看 N 个来源]
例外与版本变化       [查看 N 个来源]

关键事实（可折叠）
  原子 Claim 与来源
```

- 摘要正文使用结构化 Vue 组件，不把自动生成内容作为 `<pre>` 纯文本展示。
- 来源标记使用“查看 N 个来源”；展开后列出文档、标题路径、页码、有效状态和文档预览深链。
- 无法解析的旧页面与人工编辑页使用安全的纯文本降级显示，不把不可信内容插入为 HTML。
- 标题解析优先级为 Front Matter `title`、首个 H1、当前文档标题、文件名。
- 元数据卡只显示实际存在的字段；PDF、DOCX、TXT 没有可用元数据时不显示空卡。

## 数据与来源契约

### Claim 类型

在既有 `WikiClaim` 上新增 `summary_section`：

| claim_type | 用途 | 搜索 / Agent 可用 |
| --- | --- | --- |
| `summary_section` | 人读摘要段落 | 否 |
| `summary_fact` | 文档原子事实 | 是 |
| `topic_fact` | 跨文档主题事实 | 是 |
| `source_excerpt` / `manual` | 兼容既有数据与人工内容 | 按现有可信规则 |

`summary_section` 与其他 Claim 共用 `WikiClaimSource`。发布与读取都必须验证文档活动版本、Chunk 类型与序号、内容 SHA-256、文档状态和知识库开关。

`WikiPageResponse` 增加以下字段，同时保留 `content`、`summary` 与 `claims` 以兼容旧客户端：

```text
summary_sections: [{ id, title, text, position, trust_state, reason, sources }]
metadata: [{ key, label, value }]
```

`claims` 不包含 `summary_section`，避免旧的 Agent / 搜索使用者将长段落误认为原子事实。

### 元数据

Markdown 使用受限、确定性的 Front Matter 解析，仅接受白名单字段：

```text
document_id, title, version, effective_date, status,
scope, owner, supersedes, tags
```

Front Matter 只用于 Wiki 页面标题和信息卡，不作为模型指令，不直接赋予 Agent 事实可信度。无法解析、重复或超长的字段忽略并回退到标题优先级中的下一项。

解析结果保存在自动生成页面版本的 `generation_metadata` 中，以页面版本为边界；不修改既有文档详情契约。

## 生成与发布

### 两阶段生成

1. 将 Child Chunk 按每批最多 12 个输入模型，抽取带 `source_indices` 的 `summary_claims` 和 `topics`。
2. 服务端校验编号、去重事实并合并来源。
3. 模型仅基于已校验的原子 Claim，生成最多三个 `summary_sections`：概述、核心要求、例外与版本变化。若文档没有相应内容可以省略分段。
4. 每个摘要分段必须返回对应的 `source_indices`；服务端再次绑定真实 Chunk。
5. 在同一发布事务中写入页面版本、`summary_section`、`summary_fact`、主题页和目录页。

生成提示必须明确：

- 不逐条罗列文档编号、版本、标题、标签等元数据。
- 仅使用已提供的事实与来源编号，不补充原文不存在的信息。
- 概述描述目的、范围与关键结论；核心要求描述可执行规则；例外与版本变化描述替代、条件和边界。

### 失败与失效

- 摘要分段 JSON 非法、没有来源或引用越界时，任务按现有重试机制失败，不能发布半成品。
- 来源失效后对应摘要分段保留并标为 `needs_review`；前端显示来源失效提示，Agent、搜索和主题页不使用该段。
- 自动生成遇到人工编辑或回滚版本时，沿用现有候选版本与审核发布流程，不覆盖人工版本。
- 旧页面没有 `summary_sections` 时，页面继续可读；前端以兼容模式展示正文和 Claim，不把旧 Claim 伪装为新版摘要。

## 检索与 Agent 边界

- 页面元数据检索继续使用标题、摘要、别名和路径；其中 `summary` 更新为连贯的执行摘要文本。
- 原文 Chunk 混合召回、RRF、Rerank、Claim 词面排序与 MMR 不变。
- 只允许 `summary_fact` 和 `topic_fact` 进入 Wiki 检索、`wiki_search`、`wiki_read_page` 和主题页聚合。
- `summary_section` 仅用于人读页面，不计入 Agent 的 Claim / 字符预算。

## 验收标准

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| AC-001 | 打开带 Front Matter 的 Markdown 摘要页 | 标题采用 `title`，信息卡展示白名单元数据，正文不罗列元数据 |
| AC-002 | 生成多 Chunk 制度文档 | 页面有连贯概述、核心要求、例外与版本变化；覆盖首、中、尾事实 |
| AC-003 | 展开摘要分段来源 | 可查看所有来源并跳转到对应文档版本 / Chunk |
| AC-004 | 来源文档更新或删除 | 相关分段标记待核实，Agent、搜索、主题页不返回该段 |
| AC-005 | 搜索和 Agent 使用 Wiki | 只返回原子事实，不返回摘要段落，不引入重复结论 |
| AC-006 | 打开旧页面或人工编辑页 | 保持可读、无运行错误，并明确使用兼容展示 |
| AC-007 | 自动生成页面前端展示 | 不显示 `#`、`##`、`[^claim]` 等 Markdown 源码；长文本和移动端不溢出 |
| AC-008 | 自动生成与人工编辑并发 | 自动结果成为待审核候选，已发布人工版本不被覆盖 |

## 实施顺序

1. 固化失败测试：生成协议、来源绑定、标题元数据解析、检索隔离、API 与组件展示。
2. 扩展数据库约束和 Python DTO，发布 `summary_section` 与元数据。
3. 实现两阶段生成、长文档归并和标题元数据提取。
4. 更新 API、Agent 过滤和混合检索字段。
5. 更新 WikiPanel 的结构化摘要、信息卡、来源展开与兼容模式。
6. 执行后端、前端、类型、构建与可用浏览器验证；记录环境不能执行的项目。

## 非功能约束

- 所有代码注释和 Git 提交说明使用中文。
- 不使用不可信 Wiki 正文生成 HTML。
- 新数据迁移必须可升级与降级，且不删除已有来源记录。
- 已有用户未提交的文档预览改动不纳入本次提交。
